實作新功能時，思考「能不能用既有的開放原始碼解決？」在現代開發中是很自然的做法。
但如果選到不合適的軟體，之後才發現授權問題或資訊安全風險，就可能對整個專案造成嚴重影響。

光是 GitHub 上就有數不完的儲存庫，能達成同一目的的選項總是有好幾個。
不能只憑表面的人氣或星星數判斷，而需要從授權相容性、資訊安全穩健性、社群健全性、長期可維護性等綜合評估。

本指南從實務觀點說明如何適切且有效率地尋找與選擇開放原始碼軟體。

## 探索的起點：運用公司內部已導入 OSS 清單

尋找新的開放原始碼時，建議第一步先確認公司內部的已導入 OSS 清單。
這份清單收錄的軟體已通過資訊安全評估與技術驗證，導入判斷會比較順暢。不過，授權條款的遵守事項會因使用方式（公司內部使用、對外散布（嵌入式裝置、軟體產品、委外開發等）、SaaS 提供等）而不同，因此若過去核准的使用方式與這次的使用方式不同，就需要重新確認授權相容性。
很多時候，新的需求也可能用既有已導入軟體的組合來解決。

若在已導入 OSS 清單中找不到滿足需求的軟體，請確認目的或技術領域相近的軟體。
即使不完全一致，只要有部分滿足需求的軟體，就能以它為起點探索相關專案或替代方案，有效率地收斂候選範圍。

## 有效的探索方式

### 多角度收集資訊

在 GitHub 上的搜尋，先從具體的關鍵字（語言名稱 + 功能名稱）開始，再透過 Awesome 清單（例如：awesome-nodejs）或 Topics 功能探索相關專案。
同時，官方套件儲存庫（npm、PyPI、Maven Central 等）的下載統計、Stack Overflow 上推薦的工具資訊、技術部落格的實作案例等，也是重要的資訊來源。

技術社群中的討論，特別是 Stack Overflow 或 Reddit 上的實用評價，能提供官方文件中得不到的寶貴資訊。
實際運作中的疑難排解資訊，以及關於效能特性的真實心得，都是選擇時的重要判斷素材。

## 應評估的重要觀點

### 確認授權相容性

授權確認是最重要、卻經常被忽略的環節。
請在 LICENSE 檔案或 README 中確認授權條款種類，並務必評估它與你的使用方式（僅公司內部使用、對外散布、SaaS 提供）是否相容。

特別需要注意的是：修改或再散布時被要求提供原始碼的條件、即使透過網路提供也會產生提供義務的條件、超過一定規模或用途就需要購買商用授權的條件等。義務不限於這些，依使用形態而適用的義務相當多樣，因此確認各授權條款的具體條件相當重要。
詳細的判斷基準請參閱[什麼是授權條款](../compliance/what-is-a-license.md)與[有原始碼提供義務的授權條款](../compliance/source-disclosure-licenses.md)；若不清楚請洽詢 OSPO。

### 專案的活躍度與永續性

優秀的開放原始碼專案具有定期更新、社群討論活躍、多位開發者共同貢獻等特徵。
最近 6 個月內有更新，且 Issue 在數日內會有某種回應的專案，可以認為維持著健全的開發循環。

相較於依賴單一企業或個人的專案，獲得多個組織支援的專案可評價為長期可維護性較高。
是否有贊助企業、有明確的治理架構、是否有商用支援等，也是企業採用時的重要判斷素材。

### 資訊安全與可靠性

資訊安全評估不只看過去的弱點歷史，也重視對資訊安全事件的應對速度與透明度。
請透過搜尋 CVE（Common Vulnerabilities and Exposures）確認已知弱點，並評估對它們的處理速度。

優秀的專案會妥善實作自動化測試、持續整合、使用靜態分析工具、定期執行資訊安全掃描、回應負責式弱點揭露等。
這些開發流程的成熟度，是企業使用時的重要品質指標。

## 常見的判斷失誤與注意事項

只憑人氣選擇是容易犯的判斷失誤之一。
儲存庫的星星數再多，也可能不適合你的目的，或是複雜到難以維護的軟體。
此外，最新版本不一定就是穩定版，因此版本選擇也應謹慎進行。

容易被忽略的是相依性的評估。即使所選軟體本身沒問題，它所依賴的程式庫也可能潛藏授權問題、弱點或停止維護的風險。
若疏於進行涵蓋整個相依關係的評估，之後可能面臨嚴重問題。

長期影響也是重要的考量事項。
更新時的相容性、未來終止支援的風險、轉移到其他軟體的成本等，都需要在初期選擇時就先評估。

## 洽詢 OSPO 的時機

在以下情況下，請在導入前洽詢承辦人或 OSPO。
無法判斷是否需要商用授權時、對資訊安全面有疑慮時（請洽詢資訊安全部門）、遇到不在公司內部已導入 OSS 清單中的軟體而難以判斷時。

洽詢時，若能整理並提供以下資訊，OSPO 的評估會進行得更順暢。

- **使用目的：** 想解決什麼。應確認的重點會因目的而不同，請盡可能具體說明
- **使用方式：** 僅公司內部使用／散布／SaaS 提供等
- **技術細節：** 結合方式、相依性等
- **已評估的替代方案：** 依需要提供，若有的話

選擇合適的開放原始碼軟體，不只需要技術評估，也需要授權、資訊安全、社群、永續性等多面向的評估。依本指南謹慎選擇，就能在把專案風險壓到最低的同時，最大程度享有開放原始碼的好處。

若在判斷上猶豫，或評估較為複雜，請不要一個人苦惱，歡迎隨時洽詢 OSPO。承辦人清單請參閱「[什麼是 OSPO](../about/ospo.md)」。
