選擇開放原始碼軟體是對專案影響重大的重要判斷。
單靠表面的功能比較看不出來的風險與問題，之後可能造成嚴重影響。
因為選錯軟體，導致開發後期才發現資訊安全弱點、因授權問題難以繼續使用、維護停擺而必須另尋替代方案，這類情況絕不罕見。

本指南以開發者實際可用的形式，說明適切且有效率的開放原始碼評估方法。評估分階段進行，可以在維持效率的同時不漏掉重要觀點。
整體方針請參閱「[OSS 的尋找方式](../using/finding-oss.md)」。
本指南則作為其後續步驟，說明具體的評估方法。

## 評估的基本流程

評估分成以下三個階段進行。
在每個階段設定應通過的基準，並判斷是否進入下一階段。
要求完全滿足所有需求的完美開放原始碼軟體並不現實，因此建議把各階段的判斷基準設定得實用且務實。

### 第一階段：基本檢查

首先確認基本的適格性，及早排除明顯不適合的候選。
雖然商用軟體也是如此，但開放原始碼軟體的情況下，還需要考量其授權條款與商用授權差異很大，以及它是由社群專案開發的。
這個階段要迅速檢查以下項目。

**確認授權條款**
請在 LICENSE 檔案或 README 中確認授權條款種類，並判斷它是否符合你的使用方式（公司內部使用、散布、SaaS 提供）。
若是 GPL 系列或 AGPL 等有原始碼提供義務的授權條款，或需要商用授權的軟體，依使用形態應確認的條件較多，建議在這個階段就洽詢 OSPO。

**基本活躍度**
確認最近 6 個月內是否有更新、Issue 是否有回應、pull request 是否被合併。
完全停擺的專案，從資訊安全風險與未來性的觀點建議避開。

**最低功能需求**
閱讀 README 與文件，確認是否提供所需功能。
這個階段不需要詳細驗證，判斷是否滿足基本需求就夠了。

### 第二階段：技術評估

對通過基本檢查的候選，進行更詳細的技術評估。
這個階段不限於開放原始碼軟體，與導入商用軟體時幾乎沒有差別。

**確認實際運作**
若可行，請在簡單的測試環境中實際執行該軟體。
進行安裝的容易度、設定的複雜度、基本功能運作確認、是否能依文件所述運作等驗證。
理論上看起來很棒，實際用起來卻可能遇到意想不到的困難。

**效能與穩定性**
確認在預期使用條件下的運作。
請測量回應時間、記憶體使用量、CPU 負載等，評估是否滿足要求的效能基準。
此外，也請在可行範圍內確認長時間執行與錯誤條件下的行為。

**驗證整合性**
確認能否與既有系統及工具鏈適切整合。
請評估 API 的相容性、資料格式的支援、認證方式的一致性、能否納入部署流程等。

**分析相依性**
確認該軟體所依賴的其他程式庫與工具，並評估它們的授權條款、資訊安全弱點與維護狀況。
開放原始碼軟體所依賴的程式庫幾乎也都是開放原始碼軟體，對它們也需要以同樣方式評估
若相依性過多，或存在有問題的相依項目，就需要當成風險因素加以考量。

### 第三階段：資訊安全與風險評估

除技術評估外，也從資訊安全與風險的觀點綜合評估。

**確認弱點歷史**
請在 CVE (Common Vulnerabilities and Exposures) 資料庫中搜尋已知弱點，並確認它們是如何被處理的。
比弱點本身的存在更重要的評估重點，是從發現到修正的速度以及處理的透明度。

**資訊安全實踐**
評估專案對資訊安全的投入。
請確認是否有資訊安全政策、是否回應負責式弱點揭露、是否定期執行資訊安全稽核等。
在 README 或文件中記載資訊安全相關資訊的專案，可評價為資訊安全意識較高。

**專案的永續性**
評估開發團隊的多樣性、是否有贊助企業、財務基礎是否穩定等。
依賴單一企業或少數開發者的專案，可能因策略改變或人力資源問題而有持續性風險。

**社群的健全性**
請確認 GitHub 的 Insights 與 Contributors 資訊，評估是否形成活躍且多樣的社群。
有建設性討論、並具備歡迎新貢獻者文化的專案，可以期待長期發展。

## 評估時的重要重點

### 授權與合規

授權評估與技術評估並列為最重要的環節。
不能只是單純確認授權條款種類，還需要確認它與整個專案的授權使用方針是否一致。

特別是有原始碼提供義務的授權條款（GPL、AGPL 等），重點在於連同技術結合方式一起具體評估其影響範圍。
靜態連結、動態連結、行程間通訊、網路通訊等，授權條款的影響範圍可能因結合方式而改變。
細節請參閱[有原始碼提供義務的授權條款](../compliance/source-disclosure-licenses.md)。

若專案中混用多種授權條款，或含相依項目後授權條款組合變得複雜，就需要謹慎評估法律風險。

### 文件化與支援體制

**文件的品質**
請確認安裝指南、API 規格、使用範例、疑難排解資訊等是否充實。
優秀的文件能大幅降低導入成本與學習成本。
建議實際依文件操作一次，順便確認記載內容的正確性。

**社群支援**
請確認 GitHub 的 Issues、官方論壇等對問題的回覆狀況。
有活躍的社群支援時，問題解決會比較迅速，學習資源也會比較豐富。

**是否有商用支援**
在關鍵任務用途上，有時會需要 SLA 保證或專業的技術支援。
請確認是否提供商用支援，並依需要調查支援內容與價格。

## 常見的評估陷阱

1. **過度依賴人氣指標**

    如「[OSS 的尋找方式](../using/finding-oss.md)」所述，GitHub 星星數或下載數等人氣指標雖可參考，但過度依賴它們相當危險。
    即使很受歡迎，也可能不適合你的用途，或是複雜到難以維護的軟體。
    理解為什麼這個 OSS 受到關注、背後的原因是什麼，也很重要。
    「很多人在用」這個事實確實讓人放心，也代表包含錯誤在內的各種問題可能已經被發現。
    但人氣指標終究只是一項參考資訊，請更重視技術適用性與風險評估。

2. 盲信最新版本

    最新版本未必最好。它一方面包含新功能與改善，另一方面也可能包含新的錯誤與相容性問題。
    請確認是否有穩定版或 LTS (Long Term Support) 版，並依專案需求選擇合適的版本。

3. 功能過剩

    多功能的軟體看起來很吸引人，但不需要的功能太多會增加學習成本與運作成本。
    建議選擇範圍與需求相稱的軟體，優先選用簡潔易懂的。

4. 持續評估的必要性

    軟體的評估不是導入時做過一次就結束。
    隨著技術進步、專案變化與資訊安全環境改變，需要定期重新評估。
    對特別重要的軟體，請建立持續監控與評估的機制。

## 評估結果的運用與共享

評估過程中獲得的知識，不只該用於個人學習，更該作為團隊與整個組織的資產加以運用。
請把評估結果妥善文件化，用於與同事共享、未來類似專案的再利用，以及提升組織的評估能力。

評估時發現的問題點與良好特徵，只要具體記錄下來，就能成為之後決策的參考。
此外，也請記錄評估流程本身的改善點，為提升整個組織的評估能力做出貢獻。

若評估了多個候選，請製作比較表或評估矩陣，讓決策依據更清楚。
這樣既能對選擇理由負起說明責任，也能在未來檢視時作為參考資料。

- [ ] 已依公司內部方針具體化授權相容性的判斷基準
- [ ] 已明確活躍度的最低基準（例如：「必須最近 6 個月內有更新」等）
- [ ] 已依公司內部技術棧製作評估指南
- [ ] 已標準化相依性分析工具的導入與運用方式
- [ ] 已依業務重要程度明確是否需要商用支援的判斷基準
- [ ] 已建立定期重新評估的時程與流程
