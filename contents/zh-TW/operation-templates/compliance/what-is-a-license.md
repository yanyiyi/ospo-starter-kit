聽到開放原始碼軟體（OSS），或許會有「可以無條件使用」的印象，但實際上所有 OSS 都附有授權條款，必須依其條件使用。這是企業使用 OSS 時特別需要謹慎處理的重要面向。

以下將從 OSS 授權條款的基本概念、分類、風險，到遵循的實務做法，以能在現場判斷的具體程度加以說明。

## 為什麼授權條款很重要

「開放原始碼」與「公眾領域」根本不同。公眾領域的軟體是著作權不存在或已被拋棄，因此不適用授權條款的概念。
另一方面，開放原始碼是著作權人保有權利，同時在授予特定自由（使用、重製、修改、散布等）的授權條件下提供。
因為有授權條款，開發者能事先掌握「自己的程式碼會被如何使用」，使用者能事先掌握「什麼是被允許的」，雙方才能安心地交流軟體。

一旦忽視這套架構，對企業而言的風險就會變成實際的成本。
包括以侵害著作權為由的法律行動、要求停止散布、意料之外的原始碼提供義務、額外授權費用的請求、品牌受損。
特別是在企業環境中，以 SaaS 形式提供、隨產品出貨、向公司內部、子公司、合作夥伴橫向擴散等，「散布」的界線劃分是實務上的關鍵。
若在誤解的情況下推進，就會導致出貨前夕的設計退回或發佈延期。

## 授權條款扮演什麼角色

開放原始碼授權條款是軟體作者訂出自己的作品在什麼條件下許可他人使用的文件。
依著作權法，具創作性的軟體在被創作出來的當下就產生著作權。
授權條款就是把這項排他權利的一部分，在特定條件下許可給他人的機制。

授權條款大致分別記載了許可事項與義務事項。
許可事項包括使用、重製、散布、修改、商業使用等。義務事項包括保留著作權標示、隨附含著作權標示的授權文件、明示修改處、提供原始碼等。這些要素的組合造就了數量非常多的開放原始碼授權條款，各自提供不同的權利與義務平衡。

Open Source Initiative（OSI）是負責認證開放原始碼授權條款的國際組織。經 OSI 認證的授權條款，可確保滿足開放原始碼定義（OSD）全部 10 項條款（可取得原始碼、再散布的自由、可製作衍生作品、禁止對特定人士或群體歧視、禁止對使用領域歧視、技術中立等）。另外，也有許多授權條款雖未取得 OSI 認證但被廣泛使用。企業使用開放原始碼時，除了是否經 OSI 認證之外，確認各授權條款的具體條件也很重要。

## 如何理解並遵守授權條款

首先該做的，是把自己專案中的使用形態清楚地講出來。
只在公司內部執行？會修改嗎？會與其他軟體連結嗎？最終會散布給客戶嗎？會以 SaaS 形式透過網路提供嗎？
這一點若含糊，同一份授權條款也可能導出完全相反的結論。

在企業裡，「散布」的界線特別錯綜複雜。
擴散到公司內部其他部門、子公司、海外據點、合作夥伴環境，看起來像內部使用，但在授權條款上可能構成散布。
SaaS 多數情況下不構成散布，但遇到 AGPL 這類會因「透過網路提供」而產生義務的授權條款，情況就不同了。
例如，隨 Web 應用前端一起打包的 OSS，一般解釋為構成靜態檔案的再散布，因此可能產生保留原始著作權標示（Copyright 標記）、附上授權條款全文，甚至隨附 NOTICE 檔案等義務。

在實務上，導入前要先確認授權條款本文的所在位置（LICENSE、COPYING、儲存庫根目錄、各檔案標頭、NOTICE），再對照自己要如何使用該軟體（公司內部使用、散布、是否修改等），掌握什麼被許可、什麼構成義務。
篇幅長的授權條款，可以先用權利授予（grant／permission）、條件（condition／obligation）、免責（disclaimer／warranty）等關鍵字掌握結構，會比較容易讀懂。
例如像 Apache-2.0 這種明確規定專利授權與 NOTICE 處理方式的授權條款，重點在於建立再散布程式碼時不忘附上 NOTICE 的作業習慣。

授權遵循不是一次性的作業，而是一套流程。
新採用前的檢查、開發中新增相依項目時的自動偵測、發佈時的隨附文件確認、運作中對授權條款變更與專案移轉（例如：BSD→GPL 等）的監控。
把工具（SCA、SBOM、相依鎖定、簽章驗證）納入管線實現自動化，讓人力集中在界線判斷與例外審查上，是較務實的做法。

### 理解主要的授權條款分類

開放原始碼授權條款可以依其條件與義務的範圍大致分類。把授權條件整理成義務逐步增加的 5 個層級，會比較容易理解。

| 條件層級 | 概要 | 代表性授權條款範例 |
| -------- | --------- | ----------- |
| **類別 1. 附上著作權標示與授權文件** | 主要義務是保留與附上著作權標示與授權條款本文 | MIT、BSD |
| **類別 2. 附上指定資訊** | NOTICE 檔案或致謝等追加資訊也要包含在散布物中 | Apache-2.0 |
| **類別 3. 提供 OSS 的原始碼** | 需要提供 OSS 部分的原始碼（自有部分不需要） | LGPL、MPL |
| **類別 4. 提供連動軟體的原始碼** | 與 OSS 連動、結合的軟體原始碼也需要提供 | GPL |
| **類別 5. 向網路服務使用者提供原始碼** | 即使是透過網路提供服務，也會產生原始碼提供義務 | AGPL |

**註 1**：類別 4 只需要提供授權條款傳染到的部分的原始碼。
**註 2**：類別 3 的 LGPL 情況下，自有程式本身的原始碼不需要提供，但可能要求以使用者能替換程式庫並重新連結的形式（目的碼等）提供。部分授權條款也有需要提供原始碼的情況。

屬於類別 4 的授權條款（GPL 等）有義務提供授權條款傳染到部分的原始碼；GPL 尤其涵蓋靜態連結與同一行程內的動態連結，因此對使用形態的設計影響很大。
屬於類別 5 的 AGPL 更把 SaaS 提供也納入適用範圍，提供雲端服務的企業需要特別注意。
屬於類別 1、2 的授權條款義務相對較少，需要確認的事項有限。

同一個專案中也可能混用多種授權條款。
這時，確認授權條款的相容性（compatibility）、掌握不同授權條款的條件之間是否互相矛盾，就相當重要。

詳細的授權條款種類與特徵請參閱[授權條款的種類](../compliance/license-types.md)；對實務影響特別大的類別 4、5 授權條款，請參閱[有原始碼提供義務的授權條款](../compliance/source-disclosure-licenses.md)。
若能在設計階段就先對齊「靜態／動態連結」「外掛界線」「是 SaaS 還是散布」這些前提，可以減少事後返工。

### 授權條款的尋找方式與閱讀方式

在實際專案中最先讓人猶豫的是「（正式的）授權條款條文在哪裡」。
一般來說儲存庫根目錄會有 LICENSE / COPYING，個別檔案的標頭也會有簡要標記。
若有 NOTICE 檔案，其中會列出著作權人標示與專利、商標相關的注意事項。
製作散布物時，重點是**不要忘記附上原始著作權標示與授權條款本文**；使用 Apache-2.0 時則不要忘記**NOTICE 的傳遞**。

篇幅長的授權條款，先掌握章節架構再讀會比較有效率。
授予（grant）、條件（condition）、禁止（restriction）、免責（disclaimer）、保證（warranty）、專利（patent）、商標（trademark）。
只重點確認與自己使用形態相關的章節，在意的文句則依原文的語感解釋（中譯本僅供參考）。

### 常見的誤解與陷阱

企業現場常出現的誤解包括：「只在公司內部用所以無關」「SaaS 不是散布，所以不會產生 GPL 的義務」「因為公開在 GitHub 上，所以可以自由使用」「只交付建置產出物就沒問題」等。

實際上，擴散到公司內部其他法人（子公司或關係企業）或合作夥伴企業，在許多授權條款下都構成「散布」。即使是 SaaS，遇到像 AGPL 這種透過網路提供就會產生原始碼提供義務的授權條款，也會被課以與散布相同的義務。此外，公開在 GitHub 上的軟體同樣適用授權條件，並不因為公開就能無條件使用。即使只散布建置產出物，也有需要附上著作權標示與授權條款全文的情況。

這些判斷與專案的架構及散布形態密切相關，因此在設計階段就先確認是成本最低的做法。

### 應對特殊情況

有些開放原始碼軟體在特定條件下需要購買商用授權。
這些軟體採用雙重授權模式或依使用規模設限，企業使用時需要特別注意。
細節在[可選擇商用授權的 OSS](../compliance/oss-with-commercial-license-options.md)中說明。

### 持續性的授權管理

授權管理不是做過一次就結束。
隨著相依項目更新、新功能新增、使用形態變更等專案的進展，作為授權遵循判斷依據的狀況也會改變。
建議透過定期審查與稽核，持續確認是否符合最新的授權要求。

在大型專案中，可能使用數百到數千個開放原始碼元件。要以人工管理這些授權條款相當困難，因此善用專用工具並建立組織性的流程相當有效。

## 猶豫時請洽詢 OSPO

開放原始碼授權條款乍看似乎是複雜又麻煩的條件，但實際上是支撐開放原始碼生態系健全發展的重要機制。
透過正確理解與遵守，才能有效運用開放原始碼。
若有不清楚之處或在授權判斷上猶豫，請及早洽詢 OSPO。
